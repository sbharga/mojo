\begin{abstract}
Chess engines are usually described by their search and evaluation
techniques; a browser-deployed engine also has to satisfy constraints that
have nothing to do with chess.  \engine{} is a safe-Rust engine compiled to
WebAssembly and embedded in a React application, and this paper is about the
mechanisms that constraint forced: a per-move latency contract that a single
synchronous Wasm call can silently violate, a monotone cancellation
watermark that survives being raced by the position it is cancelling, a
node-rate-calibrated clock so polling stays cheap without going blind, a
repetition-aware cache and cross-worker principal-variation seeding that let
one browser tab reuse search work another instance already paid for, and a
250,000-byte gzip ceiling that is the actual cause of several evaluation
design choices usually explained the other way around.  None of \engine's
search or evaluation techniques are individually novel; what this paper
reports is what changes when they are assembled with no server, no
persistent process, and a strict per-tab time and size budget.  It also
reports a backend-free regression harness --- historical Wasm builds
extracted from git history and played against each other inside the page,
with a pentanomial SPRT computed client-side --- and measures \engine's
playing strength as an explicit function of its move budget rather than a
single number, because that is the axis a browser engine actually lives on.
\end{abstract}

\noindent\textbf{Keywords:} WebAssembly, browser systems, chess engines,
cancellation, alpha--beta search

\section{Introduction}

A native chess engine is handed a process, a CPU, and as much wall time as
the operator allows it.  A browser-deployed engine is handed none of those
guarantees outright: it competes with the page's own event loop, it is
downloaded before it can run at all, its ``stop'' command has to reach code
that is mid-recursion inside a single synchronous function call, and every
position it has ever seen disappears the moment the tab closes.  \engine{}
is a Rust engine compiled to WebAssembly \citep{haas2017wasm} and embedded in
a React application \citep{mojo2026software}; its search and evaluation are
conventional
alpha--beta chess-programming techniques, described briefly in
\cref{sec:background}.  The contribution of this paper is what those
techniques had to be wrapped in to run correctly under those constraints,
and what that wrapping costs and buys.

Four constraints shape everything past \cref{sec:background}.  First, a
\emph{per-move latency contract}: the UI promises that engine time is a
bounded maximum per move, and a single \code{analyze\_depth} call is
synchronous and uninterruptible from JavaScript's perspective, so nothing
about that promise is automatic (\cref{sec:latency}).  Second, \emph{reuse
across a position stream}: a browser session revisits positions constantly
(undo, redo, pause/resume, a background analysis thread investigating a line
the player is also about to reach), and a fixed-size in-memory transposition
table does not survive that on its own (\cref{sec:reuse}).  Third, a
\emph{download budget}: the engine must be small enough to arrive before the
player loses interest, which is a hard 250,000-byte gzip ceiling in this
project and is the actual reason several evaluation choices look the way
they do (\cref{sec:delivery}).  Fourth, \emph{no backend}: there is no
server to run regression matches on, so the comparison and validation
tooling has to run inside the same browser tab as the product
(\cref{sec:comparison}).

\Cref{sec:evaluation} reports measurements for each of these: cold-start
latency, cancellation latency, PV-seeding node savings, and playing strength
as a function of move budget rather than a single Elo number, alongside the
existing throughput and artifact-size measurements this project already
tracked in CI. \Cref{sec:limitations} discusses what these measurements do
and do not establish.

\section{Background: What \texorpdfstring{\engine}{Mojo} Inherits}
\label{sec:background}

\engine{} plays chess the way most alpha--beta engines do.  Its search is
iterative-deepening principal-variation search (PVS) over a negamax
formulation \citep{marsland1987sss}, with a transposition table keyed by a
Zobrist-style hash \citep{zobrist1970hashing} and a depth/age replacement
policy in the tradition of \citet{breuker1994tt}.  Depth-limited horizons are
stabilized with quiescence search \citep{beal1990quiescence}, and search is
narrowed selectively rather than uniformly: null-move pruning
\citep{donninger1993null}, futility and reverse-futility margins
\citep{heinz1998futility}, ProbCut \citep{buro1995probcut}, and singular
extensions \citep{anantharaman1990singular}, each behind the guard conditions
in \cref{tab:selectivity}.  Its evaluator is a handcrafted, tapered
midgame/endgame score whose 887 weights are fitted offline by outcome-labeled
logistic regression \citep{buro1995features}; a small search-parameter
surface is instead tuned by simultaneous perturbation stochastic
approximation \citep{spall1992spsa} and accepted only after a sequential
probability ratio test \citep{wald1945sprt}.  King-and-pawn endings are
resolved exactly by a small retrograde-analysis bitbase computed at
initialization \citep{thompson1986retrograde} rather than shipped as a table.
Board representation and legal move generation come from \code{cozy-chess}
0.3.4 \citep{cozychess2026}.

None of this is what makes \engine{} a \emph{web} engine.  A native
command-line build of the same search and evaluation would need almost
nothing described past this point.  What follows is specific to running
inside a browser tab.

\section{Preserving a Per-Move Latency Contract}
\label{sec:latency}

The UI's contract with the player is that the engine's move budget is a
maximum, not an estimate: a 500\,ms setting should never cost 5\,s.  Three
properties of the runtime work against that contract, and \engine{}'s
concurrency design exists specifically to defeat them.

\subsection{One engine cannot serve two searches}

\code{Engine::analyze\_depth} is a single synchronous, uninterruptible Wasm
call: from JavaScript's point of view, control does not return until Rust
does.  The UI runs two kinds of search concurrently in spirit --- the move
that is about to be played, and a background MultiPV analysis of the current
line --- and if both shared one \code{Engine} instance, a queued background
analysis call could occupy the call stack when a move request arrives,
stacking that analysis's full budget in front of the move search
(\code{web/src/engine/useEngine.ts}).  \engine{} instead gives \code{move}
and \code{analysis} each a dedicated Web Worker and a dedicated \code{Engine}
instance (\cref{fig:architecture}); they never share memory, so starting a
\code{move} search is never delayed by whatever the \code{analysis} worker
happens to be doing.  This is why \cref{sec:multipv} matters operationally
and not just as a cost curve: MultiPV=3 costs 2.8--4.1$\times$ the node count
of a single-PV search at the same depth in this project's four-position
suite, and that cost is fully absorbed by an isolated worker rather than
borrowed from the move budget.

\subsection{A stale cancel must not kill a live search}
\label{sec:cancel}

Cancelling a search sounds like a boolean, but a boolean is wrong here: if a
player moves twice quickly, two cancellations for two different requests can
be in flight, and a delayed handler for the \emph{older} one must not stop
the \emph{newer} search that has since started.  \engine{} instead threads a
monotonically increasing \emph{request id} through the stack and compares it
against an \code{Atomics}-backed watermark: a worker only treats the search
as cancelled when the stored watermark is greater than or equal to the id of
the search actually running (\code{stopSignal.ts}; \code{search/mod.rs}
\code{expired()}). A late message from request 6 cannot cancel request 7 just
because it arrives after it starts.

Cross-origin-isolated deployments back this watermark with a
\code{SharedArrayBuffer} so the Rust search loop polls it with a plain
atomic load between node batches; deployments without the COOP/COEP headers
that isolation requires fall back to cancelling between completed iterative
depths instead of mid-iteration. \Cref{tab:cancellation} measures what the
first path actually costs: with the watermark backed by a real
\code{SharedArrayBuffer} and the cancelling store issued from a separate
thread (a Node \code{worker\_thread}, mirroring the browser's
main-thread/worker-thread split), median observed cancellation latency is
under 1\,ms at every move budget tested, consistent with the calibrated
1.5\,ms polling target described next. A single-threaded harness cannot
observe this number at all --- nothing can interrupt a synchronous call from
the thread that issued it --- which is itself a small illustration of why
this mechanism has to be designed around genuine concurrency rather than
tested in isolation.

A cancelled search is also distinguished from a merely \emph{timed-out} one:
a timed-out iteration may still surface a sound partial root line, because
every root move that contributed to it finished a full search --- only a
later root move, or a deeper depth, never got the chance to run.  A
cancellation, by contrast, must surface nothing, because the position it was
searching is already stale; \code{search/mod.rs} tracks this as a distinct
\code{cancelled} flag from \code{timed\_out}, and it is asserted directly by
this repository's cancellation test. This distinction only matters for
single-PV move search: MultiPV analysis has no such partial fallback (a
truncated line count would visibly flicker the analysis panel), so it keeps
predicting ahead instead of ever returning a partial result
(\code{searchControl.ts}).

\subsection{Yielding between depths, and polling without going blind}

Iterative deepening is driven from JavaScript, one \code{analyze\_depth} call
per depth, specifically so the worker can yield back to the event loop
between depths.  The yield has to be a real macrotask
(\code{setTimeout(…, 0)}), not a microtask: a queued worker \code{message}
event --- carrying a newer cancellation --- is itself a macrotask, and a
microtask yield would let the current depth's synchronous call keep
starving it. Skipping this yield would mean a stale search's full remaining
budget stacks in front of the next request's, silently breaking the same
latency contract \cref{sec:cancel} exists to protect.

Inside one depth, the Rust node loop cannot check wall-clock time on every
node --- crossing to \code{performance.now()} is not free, and is
coarsened by browsers for timing-attack mitigation --- so it checks every
$N$ nodes instead. $N$ is not fixed: it is recalibrated every iteration from
an exponentially weighted measurement of the engine's own nodes-per-ms rate,
targeting a fixed 1.5\,ms wall-clock granularity between checks and clamped
to $[64, 4096]$ nodes (\code{calibrate\_clock\_checks},
\code{search/mod.rs}). A position where nodes are cheap gets checked more
often in node-count terms; a position where nodes are expensive gets checked
less often, so the check itself never becomes a meaningful fraction of
search time. This is also what \cref{tab:cancellation}'s sub-millisecond
numbers are downstream of: they are close to the calibration target because
that is precisely what calibration is tuned to deliver.

\section{Reusing Work Across a UI's Position Stream}
\label{sec:reuse}

A game's positions are not a random walk through the search space; a UI
session revisits them constantly through undo/redo, pausing and resuming on
the same position, and history navigation. \engine's persistent
\code{SearchCore} keeps its transposition table and ordering histories
across iterative depths and \emph{adjacent} positions within one worker, but
two problems remain: the fixed-size TT has almost certainly evicted an old
position's entries by the time a session revisits it, and the two isolated
Engine instances from \cref{sec:latency} cannot help each other by sharing
memory at all.

\subsection{A cache keyed on more than the board}

\code{AnalysisCache} (\code{analysisCache.ts}) lets the UI skip re-searching
a fen it has already solved to sufficient depth. The key cannot be the fen
alone: two boards with identical piece placement can have different correct
evaluations if their repetition history differs, since one may be a legal
draw claim and the other not.  \code{repetitionFingerprint.ts} hashes each
prior position with an FNV-1a/SplitMix64 mix and \emph{sums} the hashes
across a window bounded by the halfmove clock, rather than hashing the
sequence positionally --- the sum is commutative, so it depends on the
\emph{multiset} of recent positions (correctly reflecting how many times
each has occurred) but not on their order, which is exactly the quantity
that determines threefold-repetition status.

\subsection{Seeding one worker's search from another's}

Because the \code{move} and \code{analysis} Engine instances share no
memory, a deep analysis of the current position cannot warm the move
worker's transposition table by osmosis. \code{pvSeed.ts} instead replays a
PV explicitly: if the analysis worker already searched the current line and
its PV's first move matches the move the opponent actually played, the move
worker's \code{seed\_pv} call inserts the remainder of that PV directly into
its own TT as one-ply-shallower entries before searching the resulting
position. \Cref{tab:seeding} measures the effect across four position types
and three analysis depths, mirroring this exact ponder-hit path (search
position $A$ to depth $D$, replay the PV's continuation into position $B$
after its first move, and seed a $D{-}1$ search of $B$): warm searches use
noticeably fewer nodes than cold ones in most cells, but not uniformly ---
two of twelve cells cost more with seeding than without, because a seeded
aspiration window centered on the source score can trigger extra fail-high
or fail-low retries. Seeding is a speculative optimization, correct by
construction (the seed is always the actual continuation the position
reached) but not a strict node-count guarantee, and it is reported here as
such rather than smoothed into a single average.

\section{Delivering the Engine}
\label{sec:delivery}

Both the baseline and \code{+simd128} Wasm artifacts must stay under a fixed
250,000-byte gzip ceiling, checked in CI on every push. This is not a
target chosen after the fact to describe an already-small engine; it is a
constraint that shaped design decisions directly.

\subsection{Handcrafted evaluation as a size decision}

A modern NNUE evaluator's dominant cost is not compute, it is the trained
weight file --- typically megabytes, an order of magnitude past the entire
size budget \engine{} has for its whole engine. Retaining a handcrafted,
tapered evaluator with piece-square and feature weights fitted offline
(\cref{sec:background}) is therefore not primarily a search-speed choice:
the fitted values themselves cost nothing to ship, only the arithmetic that
combines them, which is already present in the binary regardless of the
weights' values. The 192\,KiB online correction-history table
(\code{search/correction.rs}) that compensates for the evaluator's
systematic residual error is similarly a \emph{runtime-allocated} structure,
not a shipped asset --- it costs peak memory, not download bytes.

\subsection{Compute-at-init instead of ship-a-table}

The KPK bitbase is the same trade-off in miniature: rather than shipping a
generated table, \engine{} runs a monotone retrograde fixed-point over
$2\cdot24\cdot64\cdot64$ normalized states at \code{Engine} construction and
keeps the 24\,KiB result in memory for the session, paying an
initialization-time cost invisible to the download budget. The optional
opening book follows the opposite discipline for the same reason: its
20,472-byte encoded table is excluded from the default build entirely
(Cargo feature \code{book}) because it would consume roughly a tenth of the
whole gzip ceiling for a feature most sessions do not need at all.

\subsection{Picking an artifact before downloading either}

\engine{} ships two Wasm artifacts, baseline and \code{+simd128}, and each
worker picks between them \emph{before} downloading either: a 29-byte SIMD
validation module is checked against \code{WebAssembly.validate} first
(\code{wasmFeatures.ts}), so a browser without fixed-width SIMD support never
fetches an artifact it cannot run. \Cref{tab:artifacts} shows what that
second artifact actually costs: 2,760 raw bytes and 285 gzip bytes over
baseline, essentially free against the ceiling --- but \cref{fig:throughput}
in \cref{sec:evaluation} shows its measured single-PV throughput benefit on
this platform is a geometric mean of $+0.26\%$, positive but small enough
that the two facts have to be reported separately: cheap to ship is not the
same claim as fast to run, and this project's CI keeps both artifacts under
the same ceiling rather than picking one based on which claim sounds better.

\section{Evaluation}
\label{sec:evaluation}

All measurements use an Intel Core Ultra 5 235 (14 visible cores, 24\,MiB L3
cache), 64-bit Linux under WSL2, Node.js v24.19.0, Rust 1.97.1. Each
Wasm-facing measurement instantiates a fresh \code{Engine} so an earlier
position or configuration cannot warm shared state; every reproduction
script lives under \code{paper/scripts/} and writes the CSV it is plotted
from, so every number below is regenerable from the checked-in repository
rather than transcribed.

\subsection{Cold start: the number a browser session actually waits on}

Throughput benchmarks assume the engine is already warm; a browser session
does not start there. \Cref{tab:coldstart} splits the wait into Wasm
compile/instantiate and the first \code{analyze\_depth} call at a 100\,ms
budget --- the app's minimum think-time setting --- median of 15 fresh
instantiations per artifact.  Instantiation itself is a few milliseconds;
essentially the entire cold-start cost is the deliberate 100\,ms search
budget, meaning a session is playable within roughly one think-time interval
of the module finishing download, not meaningfully slower.

\Cref{fig:throughput} shows substantial position dependence: baseline median
throughput ranges from 2.17 million nodes/s (tactical) to 3.67 million
(endgame), reflecting differing work per node across positions rather than a
fixed machine rate. SIMD's effect is small and mixed --- $-0.79\%$,
$+0.49\%$, $-1.95\%$, $+3.35\%$ across the four positions, geometric mean
$+0.26\%$ --- with identical cumulative nodes, best move, and score in every
pair, isolating code-generation speed from search divergence. This is why
\cref{sec:delivery} reports SIMD's near-zero size cost and near-zero speed
benefit as two separate facts rather than one recommendation.

At depth nine, MultiPV=3 costs 2.8--4.1$\times$ single-PV's node count across
the four positions (44,335$\to$122,770 at the start; 111,328$\to$306,474 in
the middlegame), which is the cost \cref{sec:latency}'s worker isolation
exists to keep off the move budget.

\subsection{Playing strength as a function of move budget}
\label{sec:strength-budget}

A native engine's Elo is reported against a fixed time control because that
is the deployment condition. A browser engine has no single deployment
condition --- the UI's move-time slider ranges 100--10{,}000\,ms --- so
reporting one Elo number the way a native-engine paper would is itself
misleading: it silently picks one point on a curve and presents it as the
whole answer. \Cref{fig:elo-budget} instead measures \engine{} against
Stockfish 18 Lite \citep{stockfish2026,stockfishjs2026} (the same
single-threaded Wasm build bundled in the web app) at equal per-move time, sweeping \engine's move budget against a fixed
calibrated \code{UCI\_Elo} tier, with every opponent move drawn from a fresh
UCI \code{go movetime} search at the identical budget. Games use
color-swapped balanced openings with score/draw-streak adjudication
identical in structure to this project's self-play harness
(\code{engine/selfplay.mjs}); sample sizes are small by necessity (a handful
of opening pairs per cell, run against a real Stockfish process rather than
a second lightweight Wasm engine), so this is reported as a directional
trend with labelled budgets, not a tight interval.
\Cref{tab:elo-tier} additionally holds \engine's budget fixed at 3{,}000\,ms
and raises the opponent tier toward Stockfish's calibrated \code{UCI\_Elo}
ceiling (3190), to test directly whether more thinking time closes the gap
against a near-maximum calibrated opponent rather than only a fixed one.

The result does not confirm the naive expectation that more time
monotonically buys \engine{} more relative strength. Against the fixed
SF\,2400 tier (\cref{fig:elo-budget}), \engine{} scores 66.7\% at 100, 500,
and 1{,}000\,ms alike, then drops to an even 50\% at 3{,}000\,ms; against
rising tiers at a fixed 3{,}000\,ms budget (\cref{tab:elo-tier}), it beats
SF\,2400 (62.5\%), loses to SF\,2800 (37.5\%), and draws every one of four
games against SF\,3190. A plausible mechanism: \code{UCI\_LimitStrength} caps
Stockfish's move selection, not its search depth, so a longer shared budget
lets Stockfish's own search converge onto stronger moves under the same noise
layer, narrowing rather than widening \engine's edge. The all-draw SF\,3190
cell is also consistent with adjudication triggering on solid play from both
sides at long budgets rather than with \engine{} matching Stockfish's
near-maximum tier. With four to six games per cell this is a directional
signal, not a tight interval (\cref{sec:limitations}). What it does support:
at the 100--1{,}000\,ms budgets the UI offers by default, \engine{} outperforms
a calibrated SF\,2400 opponent, and at no tested budget did it reliably beat a
calibrated tier above 2400.

\subsection{Regression test suite}

The native Rust suite has 83 \code{\#[test]} functions covering perft positions, legal PVs, forced
mate, repetition and fifty-move draws, incremental evaluation agreement, KPK
normalization, SEE thresholds, TT collision and mate-score behavior, every
move-picker stage, pruning guards, timeout semantics, clock calibration,
MultiPV distinctness, and memory-layout assertions on the fixed-size
structures in \cref{tab:artifacts}. Tests cannot establish playing strength,
but they protect the invariants \cref{sec:latency,sec:reuse} depend on ---
in particular, that a real cancellation never surfaces a partial line, and
that a stale request watermark never stops a live one --- which selective
search and concurrent cancellation could otherwise violate silently.

\section{Backend-Free Regression Testing in the Page}
\label{sec:comparison}

There is no server behind this project, which means there is nowhere to run
a regression match except the same static page the product ships as. The
comparison lab (\code{web/src/comparison/}, reachable at \code{\#/compare})
solves this by treating \emph{git history itself} as the engine-version
catalog: a build script (\code{prepare-engine-versions.mjs}) walks every
commit that touched the compiled Wasm artifact, extracts each historical
\code{mojo\_engine\_bg.wasm} and its glue module directly from git object
storage, and screens each one against a fixed set of required export
fragments (\code{export class Engine}, \code{analyze\_depth(}, \dots) so an
incompatible ABI from an old commit is silently excluded rather than
crashing the page that loads it. The result is served as a static JSON
manifest --- no server-side build matrix, no artifact registry, just
commits the repository already has.

The page itself plays any two catalog versions against each other: workers
equal to $\min(4, \text{cores}-1)$ load one engine build apiece, play
color-swapped balanced opening pairs, and adjudicate identically to the
offline self-play harness. What is unusual is that the SPRT itself runs
client-side: \code{match.ts} bins completed opening pairs into a pentanomial
distribution and accumulates a log-likelihood ratio against $\mathrm{H}_0{:}\allowbreak+0$
and $\mathrm{H}_1{:}\allowbreak+10$ Elo \citep{wald1945sprt}, the same test this project's
offline SPRT gate uses to accept search-tuning candidates, but computed
entirely in a page a visitor is looking at, with no backend to compute it for
them. A visitor can compare, say, last month's search-tuning candidate
against the version currently deployed and read the same statistical
decision this project's own CI pipeline would have made, without installing
anything.

\section{Discussion and Limitations}
\label{sec:limitations}

Most of what makes \engine{} small and fast is reuse across the concerns this
paper separated for exposition: the TT move feeds root order, PVS,
singular tests, and quiescence; a PV seeded across workers only helps
because the search and the cache agree on what a position \emph{is}
(\cref{sec:reuse}); the same node-count clock check that keeps polling cheap
(\cref{sec:latency}) is what makes cancellation latency small enough to
report in milliseconds rather than iterations. That reuse is also why these
mechanisms are difficult to evaluate in isolation --- \cref{tab:cancellation}
needed genuine thread concurrency to measure honestly, and an
otherwise-reasonable single-threaded harness would have reported numbers
dominated entirely by artifacts of the harness rather than the mechanism.

The strength measurements in \cref{sec:strength-budget} are the most
constrained in this paper: small opening-pair counts against one Stockfish
build, on one machine, is a trend, not a tournament result, and a
performance rating against a \code{UCI\_LimitStrength} tier is not the same
claim as a rating against unconstrained Stockfish. The throughput and
cold-start numbers likewise describe one Node/V8 build under WSL2, not
Chrome, Firefox, Safari, mobile CPUs, or thermal-throttled hardware. The
cancellation-latency mechanism is platform-independent by construction (an
\code{Atomics} watermark at a calibrated node-count interval), but its
measured latency is not: a slower or more contended CPU changes how many
nodes fit in the 1.5\,ms target, and therefore how promptly cancellation is
observed. Future work should extend the budget sweep to a finer grid and more
opening pairs, repeat the cold-start and cancellation measurements inside an
actual browser, and check the comparison lab's client-side SPRT against the
offline harness's decisions on the same historical candidates.

\section{Conclusion}

None of \engine's search or evaluation techniques are new to computer chess.
What this paper described is what it took to run that inherited technique
under constraints a native engine never faces at all: a per-move latency
contract enforced across two memory-isolated Wasm instances and a monotone
cancellation watermark rather than a boolean; a repetition-aware cache and
explicit cross-worker PV replay standing in for the shared memory two
threads would otherwise have; a 250,000-byte gzip ceiling that is the actual
cause of the handcrafted evaluator, the init-time KPK bitbase, and the
feature-gated opening book, not an afterthought applied to an
already-decided design; and a regression lab that computes its own SPRT
inside the same static page it is testing, because there is no server to do
it elsewhere. The broader lesson is that ``chess engine'' and ``web chess
engine'' are different design problems even when the search tree underneath
is identical, and the second problem is the one this paper is actually
about.
